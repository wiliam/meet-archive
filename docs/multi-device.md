# Хаб: консолидация встреч с нескольких устройств

Один экземпляр админки на сервере собирает встречи со всех Mac, чтобы поиск по
транскриптам, темам и action items шёл по всему корпусу сразу.

## Модель

```
Mac #1 ─┐ archive_summit_meetings.py  (не меняется)
        │       ↓ summit-archive/database.sqlite   ← push читает mode=ro
        └─ push_to_hub.py ──HTTPS + Bearer──┐
                                             │
Mac #2 ─┘ то же                              ▼
                                Traefik → meet-archive (Dokploy)
                                             ▼
                                /opt/meet-archive/data/database.sqlite
```

Три свойства, которые стоит держать в голове.

**Push читает архив, а не живую базу Summit.** Модель безопасности прунинга
целиком опирается на «встреча подтверждённо есть в архиве», и второй процесс в
живой базе — ровно то, от чего предостерегает `CLAUDE.md`. Клиент отказывается
работать с каталогом, не похожим на архив. Следствие: на хаб не может попасть
встреча, не прошедшая архивацию.

**Сервер только накапливает.** Push умеет добавлять и обновлять, но не удалять.
Локально архив можно чистить, не боясь потерять историю; удаление на сервере —
ручная операция.

**Аудио остаётся на устройстве.** На сервер едут строки БД и `document.md`.
Карточка встречи показывает, на каком устройстве лежит запись.

## Что именно уезжает

Исключается на устройстве, до отправки:

| Что | Почему |
|---|---|
| `transcription_segments.word_confidences_json` | 39.9 МБ из 66 МБ базы при 1.6 МБ собственно текста; админка колонку не читает |
| `speakers.embedding` | голосовой отпечаток, на публичном сервере бесполезен и нежелателен |
| `chat_sessions`, `chat_messages` | UI нет, «вне скоупа» в `admin-design.md` |
| `calendar_events` | не читается нигде и несёт UNIQUE-капкан `(provider, external_id)` |
| `*.m4a` | по решению: записи не покидают устройство |

Практический эффект: консолидированная база 62 встреч — 18 МБ вместо 66 МБ,
бандл одной встречи — сотни килобайт в gzip.

## Почему слияние — отдельный код, а не тот же архиватор

`folders.name`, `tags.name` и `summarization_templates.name` объявлены UNIQUE, а
архиватор вставляет справочники через `INSERT OR REPLACE`. В SQLite `REPLACE`
разрешает конфликт по UNIQUE **удалением** старой строки, а `document_tags.tag_id`
объявлен `ON DELETE CASCADE`. Тег «work» со второй машины (другой UUID, то же имя)
удаляет строку первой и каскадом уносит все её связи тегов. Молча.

`ingest.py` вместо этого сводит справочники по имени **до** вставки и переписывает
ссылающиеся строки. Инвариант модуля: ни одного `INSERT OR REPLACE` в таблицу с
UNIQUE по тексту. Он закреплён тестом, который читает исходник, — потому что
сломать его случайным рефакторингом легко, а заметить последствия трудно.

Смежное: у `documents.folder_id` внешнего ключа нет вовсе, поэтому висячую ссылку
`PRAGMA foreign_key_check` не поймает. Тесты проверяют её явным LEFT JOIN.

## Протокол

Все маршруты требуют `Authorization: Bearer <токен>`, кроме `/api/ingest/health`.

| Маршрут | Назначение |
|---|---|
| `GET /api/ingest/health` | живость, без авторизации |
| `GET /api/ingest/state` | что у сервера уже есть: `document_id → modified_date, content_hash, device_id`, плюс список миграций |
| `POST /api/ingest/meeting` | бандл одной встречи, `Content-Encoding: gzip` |
| `PUT /api/ingest/meeting/{id}/document.md` | markdown отдельным запросом |

`device_id` берётся из токена, а не из тела запроса: иначе одно устройство могло
бы писать записи разводки справочников от имени другого.

Ответ `POST`: `201 created`, `200 updated`, `200 unchanged` (совпал
`content_hash`), `400` (контракт), `409 schema_ahead`, `413`, `503`.

### Состояние живёт на сервере

Локального файла синхронизации у клиента нет. `archive-state.json` хранит одно
wall-clock значение `last_successful_sync_at`, и при двух машинах правки одной
молча пропускались бы из-за отметки другой. Вместо этого клиент спрашивает
`/api/ingest/state`, поэтому `modified_date` всегда сравнивается только с копией,
записанной этой же машиной. Часы разных машин не сравниваются никогда.

Побочный эффект: стирание сервера самовосстанавливается — следующий push зальёт
всё заново.

### Дрейф схемы

Бандл несёт список миграций Summit. Устройство старше сервера — принимается с
предупреждением. Устройство новее — **409 `schema_ahead`**, без авто-ALTER: у
архиватора есть живая база как эталон, у сервера эталона нет, и молчаливый DDL на
общей базе хуже громкого отказа. Лечится перегенерацией схемы:

```bash
./scripts/dump-schema.sh summit-archive/database.sqlite > summit-archive-admin/schema.sql
git diff summit-archive-admin/schema.sql   # чистый DDL + идентификаторы миграций
```

## Развёртывание

1. На основном Mac довести архив до актуального состояния и сгенерировать схему:

   ```bash
   ./summit_archive.sh sync
   ./scripts/dump-schema.sh summit-archive/database.sqlite > summit-archive-admin/schema.sql
   ```

2. На VPS подготовить том. **`chown` обязателен**: открытие WAL-базы даже в
   режиме `mode=ro` требует права записи в каталог ради файла `-shm`, и
   несовпадение владельца — самая вероятная ошибка первого развёртывания.

   ```bash
   mkdir -p /opt/meet-archive/{data,backups}
   chown -R 10001:10001 /opt/meet-archive
   ```

3. Создать приложение в Dokploy из этого репозитория. Переменные окружения —
   по списку в `.env.example`; секретов в репозитории нет. Токен на устройство:
   `openssl rand -hex 32`.

4. Дым-проверка:

   ```bash
   curl https://<домен>/api/ingest/health
   curl -u "$ADMIN_USER:$ADMIN_PASSWORD" https://<домен>/
   ```

   Ожидается **пустой список встреч**, а не страница «архив не готов»: её
   обработчик срабатывает на `no such table`, а со `schema.sql` таблицы есть и
   просто пусты.

5. Первая заливка — сначала частично:

   ```bash
   export MEET_ARCHIVE_HUB_URL=https://<домен>
   export MEET_ARCHIVE_HUB_TOKEN=<токен устройства>
   ./summit_archive.sh push --dry-run
   ./summit_archive.sh push --limit 3
   ./summit_archive.sh push
   ```

6. Второе устройство подключается своим токеном. Полезно записать `count(*)` по
   `folders` и `tags` до и после: расти они должны только на реально новые имена,
   и ни одна встреча первой машины не должна потерять тег.

7. Ночной бэкап на хосте — через `.backup`, а не `cp`: он безопасен при живом
   писателе.

   ```bash
   sqlite3 /opt/meet-archive/data/database.sqlite \
     ".backup /opt/meet-archive/backups/db-$(date +%F).sqlite"
   ```

## Расписание на устройстве

```bash
./summit_archive.sh sync-and-push
```

Токен лучше держать в файле с правами 600 и передавать `--token-file`: значение
из командной строки видно в `ps`.

> **Ловушка TCC.** Под launchd процесс атрибутируется на `/bin/bash`, и чтение
> репозитория в `~/Documents` запрещается молча, без запроса прав — см.
> `why-a-launcher-not-a-desktop-app.md`. Из Терминала при этом всё работает.
> Агент нужно проверять отдельно, иначе это выглядит как «push сломан».

## Роли

| | `local` (по умолчанию) | `server` |
|---|---|---|
| Привязка | 127.0.0.1 через `serve.sh` | 0.0.0.0 в контейнере, TLS на Traefik |
| Basic Auth | опционален | обязателен, проверяется при старте |
| `/sync` | есть | не регистрируется |
| Маршруты ingest | только при заданном `INGEST_TOKENS` | есть |
| Аудио | есть | нет, вместо него подсказка об устройстве |

В серверной роли приложение **отказывается стартовать** без `ADMIN_USER`,
`ADMIN_PASSWORD` и `INGEST_TOKENS`. Это осознанно: иначе потеря переменной
окружения молча выкладывает архив личных встреч в открытый доступ.
